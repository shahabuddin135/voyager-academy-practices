HARNESS — controls each action inside Step 4
1 · CONSTRAINAllow temp cleanup. Ask before installs. Deny secrets and photos.
2 · INFORMGive folder map, app policy, backup rules, and tool descriptions.
3 · VERIFYCheck hashes, free-space result, backup integrity, and exit codes.
4 · CORRECTRoll back, retry safely, and turn repeated failure into a new rule.
5 · ESCALATEStop and ask a person when risk or uncertainty exceeds policy.

Do not mix these layers

L
Loop questionWhat starts the work, what repeats, what survives, and what stops it?
H
Harness questionFor this action, what may the model do, what does it know, how is it checked, and what happens on failure?

The loop decides to run every morning until the PC has 15 GB free. The harness decides that deleting Temp is allowed, uninstalling software needs approval, and opening .env is denied.

Nine concepts, rebuilt in the PC-control scenario

Each card separates two ideas that solve different engineering problems.

1

Harness vs Loop

Action control vs work cycle

Harness: the rules and mechanisms around each model action. Loop: the structure that starts a beat, repeats work, remembers state, and decides when to stop.

At 6:00 AM, the loop starts. Before deleting a temp file, the harness checks folder scope, permission, and verification.
Loop ownsHeartbeat, beat, retries, spine, stopping condition.
Harness ownsTools, context, permissions, checks, logs, rollback.
Exam trap: a deny rule is not a heartbeat; a schedule is not a guardrail.
2

Prompt Rule vs Guardrail

Advice vs enforcement

Prompt rule: “Never open personal photos.” It guides the model. Guardrail: the photo folder is outside the tool’s allowed paths. The action cannot run.

The agent gets confused by a folder name. A prompt may be ignored; a file-system deny rule blocks access anyway.
RuleUseful for judgment and project habits.
GuardrailUsed when the cost of failure is too high for words alone.
Test: Can the model disobey it? If yes, it is guidance, not a hard guardrail.
3

State Spine vs Account Spine

Owned task memory vs vendor continuity

State spine: your repo file or database recording task state. Account spine: sessions and files saved by a hosted agent service across devices.

pc-maintenance-state.json says backup 4/7 finished. A cloud agent account also remembers the chat and files, even on your phone.
State spinePortable, versioned, designed by you, tied to the job.
Account spineConvenient, vendor-hosted, tied to the account and platform.
The account spine can store continuity, but it is not automatically your governed System of Record.
4

Maker–Checker vs Worktree Split

Trust separation vs edit isolation

Maker–checker: one actor changes, another judges. Worktree split: separate working folders stop parallel agents from changing the same files.

Agent A prepares an app-update script. Agent B checks it. A separate worktree keeps that experiment away from the live automation files.
Maker–checker solves“Can we trust this work?”
Worktree solves“Will two workers collide?”
Isolation does not prove quality. Review does not stop file collisions.
5

Typed Output vs Prose Verdict

Machine branch vs human interpretation

Prose: “Looks mostly fine, though the backup may need attention.” Typed: {"verdict":"HUMAN_REQUIRED","risk":"high"}.

The loop must decide whether to commit, retry, or alert you. It cannot safely branch on vague language.
Typed output givesSchema validation, safe branching, clear missing fields.
Prose givesExplanation for people, but weak control for code.
Best pattern: typed decision fields plus a human-readable reason.
6

Bar vs Baseline

Pass policy vs recorded reference

Bar: the minimum you choose. Baseline: the measured result from a known version, model, rubric, and date.

Safety bar: 100% on “never touch protected folders.” Baseline: version 1.4 passed 47 of 50 total eval cases last Friday.
Bar asks“Is this acceptable?”
Baseline asks“Did this get better or worse than before?”
Do not move the bar to match a bad score. Do not treat the baseline as the moral definition of good.
7

Drift vs Regression

External behavior change vs local breakage

Regression: your prompt, code, rule, or tool change made results worse. Drift: behavior changed although your local system stayed the same.

After you edit the cleanup policy, protected-folder accuracy drops: regression. Nothing changes locally, but a hosted model update causes the drop: drift.
Catch regressionRun evals on every harness change.
Catch driftRun the same evals on a schedule.
A green CI run after your last commit cannot detect a model change that happens next week.
8

Runtime Home vs Quality

Availability vs correctness

Runtime home: where the process stays alive. Quality: whether its spec, tools, policy, checker, and evals produce good work.

Moving the 6:00 AM beat to a server means it runs while your PC is off. It does not fix a checker that approves broken backups.
Runtime improvesUptime, scheduling, remote access, recovery ownership.
Harness improvesSafety, evidence, repeatability, correction, escalation.
Cloud execution can make a bad agent fail more reliably and more often.
9

Vertical vs Narrow Agent

Governed business domain vs one worker

Narrow agent: one Digital FTE with one job. Vertical: the governed domain system that can manufacture many related workers.

“PC Backup Agent” is narrow. A “Managed IT Operations” vertical contains policy, corpus, expert knowledge, tools, evals, and workers for backup, patching, inventory, and incident triage.
Narrow agentOne outcome and one operating role.
VerticalReusable domain base for many workers and customers.
A collection of documents is not a working vertical without committed domain expertise and governance.

How the PC agent grows into a harness

Every stage begins with a real failure. The fix becomes a permanent system layer.

Stage 0 — Bare LLM

Problem: it can explain actions but cannot safely perform them.
Control 05/100

Add OS tools for reading disk space and listing files. The model is now useful, but its power has grown faster than its safety.

Stage 1 — Tool-using agent

Problem: it can call a delete command on the wrong path.
Control 18/100

Fix: add allow / ask / deny permissions and path scope. Protected folders become mechanically unreachable.

Stage 2 — Informed agent

Problem: safe actions can still be stupid because the model lacks PC policy.
Control 32/100

Fix: add a short rules file, folder map, app-update policy, backup procedure, and precise tool descriptions.

Stage 3 — Verified actions

Problem: “backup complete” may be false.
Control 49/100

Fix: require hashes, file counts, exit codes, and free-space measurements. Done becomes a test, not a sentence.

Stage 4 — Maker–checker

Problem: the same agent that acted can rationalize its own mistake.
Control 62/100

Fix: a separate checker reviews the plan, tool log, and evidence. Only its verdict can move the loop forward.

Stage 5 — Typed verdicts

Problem: prose review cannot drive safe automatic branching.
Control 70/100

Fix: use a schema with verdict, risk, evidence, failed_checks, and required_human_action.

Stage 6 — Checkpoints and correction

Problem: partial failure leaves the PC in an uncertain state.
Control 78/100

Fix: create restore points, backup manifests, and staged changes. Roll back, classify the failure, then add a permanent harness rule.

Stage 7 — Loop and state spine

Problem: each new session forgets the previous run.
Control 84/100

Fix: add heartbeat, beat, capped retries, stopping condition, and a state file read first and updated last.

Stage 8 — Evals, bars, and baseline

Problem: one successful morning does not prove stable quality.
Control 91/100

Fix: build a golden set: protected folders, locked files, low disk, failed network, corrupt backup, injection in filenames. Set category bars and record a baseline.

Stage 9 — Runtime migration

Problem: the loop misses 6:00 AM when the laptop is closed.
Control 91/100 + uptime

Fix: move the clock and worker to a reliable runtime. Re-run evals there. Quality does not rise merely because uptime rises.

Stage 10 — Vertical tuning

Problem: one PC agent is useful but not yet a repeatable business system.
Reusable domain

Fix: work with an IT domain expert, build a governed corpus and policy base, then manufacture narrow workers for backup, updates, inventory, and incident triage.
